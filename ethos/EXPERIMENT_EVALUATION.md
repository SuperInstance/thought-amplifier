# Experiment Evaluation — EXP1 (Reflex Hit Rate) and EXP2 (Semantic Gradient)

**Author:** Claude Opus, acting as Ethos (evaluative faculty)
**Date:** 2026-08-03
**Verdict, in one line:** neither experiment validates the DCA thesis, and only one of them (EXP1) actually falsifies anything — EXP2 doesn't fail the thesis, it fails to test it, and its own report claims more than its data supports.

---

## EXP1: Reflex Hit Rate

### What actually happened

The pre-registered hypothesis was "cognitive content has a lower reflex hit rate than command routing, due to higher semantic variability." The primary, full-scale (n=100) result, using TF-IDF:

| | Cognitive | Command | Target (C2) |
|---|---|---|---|
| Hit rate @ ≥0.55 | 13.1% | 6.1% | ≥40% |

Two things are true here and the report only fully reckons with one of them.

**True finding 1 (correctly reported): both domains miss the 40% target badly.** Neither cognitive content nor command routing clears the bar under TF-IDF. This is a clean, honest, well-executed negative result — n=100, proper incremental simulation (each item compared only against previously-seen items, which is the right way to simulate a growing reflex store), full threshold-sensitivity table, real effect sizes. Good work.

**True finding 2 (under-reckoned with): the hypothesis is reversed, not just unconfirmed.** Cognitive similarity (13.1%) is *higher* than command similarity (6.1%) — the opposite of what was predicted. The report's "Statistical significance: Mann-Whitney p = 1.000000 (not significant)" bullet is presented as inconclusive, but that test was run one-sided for "cognitive < command" — the wrong tail, given what the data actually shows. The two-sided Welch's t-test, run correctly, comes back significant at p < 0.000001 with a large effect (d = -0.83) — in the direction *opposite* the hypothesis. This isn't "no evidence either way." It's evidence the original hypothesis was wrong, dressed up by an incorrectly-tailed second test to look like a null result. That's a bug in the analysis, not in the data, but it changes what the experiment is entitled to conclude.

**A confound that undercuts the comparison itself:** both the cognitive and command corpora were generated by uniform random sampling over a combinatorial template space (30 scenarios × 20 observations × 20 intentions for thoughts; 30 verbs × 30 objects × 16 directions × 20 locations × 15 modifiers for commands — 4.3M+ distinct combinations). Real command routing, the domain the 40–80% precedent numbers (Pincher, Lever Runner) were measured on, is Zipfian: a small set of commands recur constantly ("go north," "check door"). Uniform sampling over millions of combinations manufactures near-zero repetition by construction — which is likely *why* command hit rate came in at 6.1% instead of the 50–60% the dissertation expected, not because commands are intrinsically harder to match than the precedent systems found. This means EXP1 doesn't actually reproduce the conditions under which the precedent numbers were measured, for either domain. The comparison between cognitive and command hit rate is real; the comparison to the dissertation's inherited targets is not, because the sampling procedure doesn't resemble production traffic in either arm.

### The "neural rescue" section doesn't hold up

The report's actual verdict is "**SUPPORTED** when using the production embedding model," based on an 8-item sample embedded with nomic-embed-text, showing 93% pairwise similarity ≥0.55, versus the 100-item TF-IDF result. I'd reject this conclusion as currently supported, for reasons the report itself lists as "limitations" but doesn't let affect the verdict:

- **n=8, not n=100.** The number that gets carried into the headline ("Claim C2 is SUPPORTED") comes from a sample 12.5× smaller than the one used to falsify it under TF-IDF. That's not a like-for-like comparison; it's a hopeful spot-check overriding a rigorous negative result.
- **"Cross-validation" is the wrong term** for what this is — it's a pairwise similarity check on a small held-out sample, not cross-validation in any technical sense. Worth fixing because it reads as more rigorous than it is.
- **Templated data, not generated thoughts.** All 8 items (and the full 100) are drawn from the same fill-in-the-blank template pool ("Standing here at the X, I notice Y"). Neural embedders are very good at detecting shared syntactic/thematic scaffolding — which is exactly what a template generator produces regardless of the underlying "thought" content. High similarity here may be measuring "these all came from the same template" rather than "these are semantically similar cognitions," which is a materially different claim from the one C2 needs. Real Granite-generated thoughts (which EXP2 actually has 11 examples of) would be a fairer test and were sitting right there.
- **No threshold-sensitivity table for the neural run**, unlike the thorough one done for TF-IDF. We don't know how the 93% figure moves at 0.60, 0.65, 0.70 — the TF-IDF table shows hit rate is highly threshold-sensitive (92.9% at ≥0.10 down to 0% at ≥0.75), so a single point estimate at 0.55 for 8 neural samples is a thin basis for a claim this load-bearing.

**Net assessment on EXP1:** the falsification of the TF-IDF hypothesis is real and should stand. The claim that neural embeddings rescue C2 is not established by this experiment — it's an inference from a much smaller, differently-composed sample, presented with more confidence than it earns. If I'm ranking it: **the hypothesis as stated is falsified; the fallback claim is unproven, not confirmed.**

## EXP2: Semantic Gradient

### Credit where due: the design is good

The four-phase structure (baseline → intervention → reversal → sham) directly operationalizes the review's central objections — Q1 tests whether the intervention helps at all, Q2 tests whether gains are real (they should vanish on reversal) or an artifact, Q3 tests real-vs-sham (the actual point: is this the Conductor's intelligence or just novelty bias), Q4 tests whether the sham alone produces a placebo bump. This is exactly the ablation structure `CLAUDE_REVIEW.md` says is missing from the dissertation's protocol. Designing it this way, and explicitly cross-referencing four different reviewers' objections (Claude, DeepSeek V3.1, Seed-2.0-pro, DeepSeek R1) in the writeup, shows the team is taking criticism seriously rather than defensively. That's worth saying plainly before the rest of this section, which is not kind to the execution.

### What the data actually contains

| Phase | Attempted | Succeeded | Failed |
|---|---|---|---|
| baseline | 20 | 9 | 11 |
| intervention | 3 | 2 | 1 |
| reversal | 0 | 0 | 0 |
| sham | 0 | 0 | 0 |

The run did not fail *at* reversal or sham — it never *reached* them. Three of the four pre-registered phases produced either almost no data (intervention) or none (reversal, sham). This is the same GPU/CUDA failure mode `ADVISORY_BRIDGE.md` already diagnosed (`size_vram=0`, silent fallback to CPU, which cannot finish generation inside timeout) — and it has now recurred across at least two separate attempts, which means whatever fix was applied after the first crash either wasn't applied here or didn't hold. Two independent runs, same failure, is a pattern, not a fluke.

### A statistical bug that inflates the apparent conclusiveness of the result

This is the finding I'd flag as the most important thing in this document, because it isn't in either report's own limitations section, and it changes how much weight the headline verdict deserves.

Look at Q2, Q3, and Q4 in the report: each one runs a t-test and Mann-Whitney comparison against a phase with **zero recorded observations**, and each one reports a mean of `0.000 ± 0.000` for that phase rather than "no data." A phase with n=0 is not a phase with mean 0 — it's an absent measurement. Treating it as "all zeros" and then running a t-test against it (which the report does, producing `p=1.0000, ns` four times over) manufactures a *statistically dressed non-result* that reads, at a skim, like "no difference detected" — when the honest description is "not measured." This is a bug in whatever script produced the comparison tables (`exp2_analyze.py` / `update_report.py`), not a property of the underlying phenomenon, and it should be fixed before any p-value from this pipeline is trusted again. It's a more serious problem than the underpowering the report does acknowledge, because underpowering is visible in the numbers (small n, wide CIs) while this is invisible — it looks like a completed statistical test.

**The only real comparison in the entire experiment is Q1: baseline (n=9) vs. intervention (n=2).** That comparison is honestly reported (trend toward improvement, Δ=+0.13 on the total score, p=0.85, not significant) and I have no complaint about how it's described in isolation. But n=2 for the treatment arm is not a result — it's two data points. This tells us essentially nothing about whether directed prompting improves quality, in either direction.

### The headline verdict overclaims

The report's verdict is **"SEMANTIC GRADIENT IS NOT DETECTABLE."** Read against what was actually measured, this should be **"semantic gradient was not tested — the sham arm, the reversal arm, and 85% of the intervention arm never ran."** The one comparison that did run (Q1) is uninformative in either direction, not negative. This matters because the sham arm specifically is, per `CLAUDE_REVIEW.md` §1.1 and this project's own `ADVISORY_BRIDGE.md`, the single most important mechanism in the entire dissertation — it's the thing that would distinguish "the Conductor works" from "any change looks like it works." It has now been attempted twice and has produced **zero data points, ever**, across both attempts. That's not a disconfirming result for DCA. It's an unresolved blocker sitting exactly where the review said the whole thesis lives or dies.

I want to be fair to the report's own limitations section — it does list "N=20 per phase may be underpowered," "no human validation of the scoring rubric," and "model may be running on CPU rather than GPU" (correctly suspecting the actual cause). The instinct is right. But listing underpowering as a caveat while still leading with a categorical verdict ("NOT DETECTABLE") undersells how little was actually measured. A more calibrated headline would change the reader's takeaway substantially, and in a project already fighting a "results are asserted, not shown" criticism from its own defense review, that gap matters more here than it would elsewhere.

## What this tells us about the production line model

This is where the two experiments say something neither one says on its own.

**The baseline phase's own success rate is a finding, independent of the semantic-gradient question:** 9 of 20 sequential, single-model, modest-token-budget (`num_predict=60`) Ollama calls succeeded. That's a 45% raw completion rate for the *simplest possible* workload the local inference stack has to sustain — no concurrency, no competing agents, no scheduler contention, just a for-loop calling the same model 20 times in a row. The dissertation's central engineering claim is a continuous thinker running at 1–2 Hz; the scheduler's "production line" thesis (`scheduler/DESIGN.md`) is that priority, fair-use, and cloud-overflow logic turn a single 6GB GPU into a system that "gets better at producing value" over time by intelligently allocating scarce compute. Both of those claims assume the compute is *available to allocate*. What EXP2 shows, again, is that the GPU's CUDA context doesn't degrade gracefully under load — it collapses outright (`size_vram=0`), and everything downstream fails silently until someone notices and restarts the service. A scheduler can be arbitrarily well-designed — and the scheduler's own unit tests do pass cleanly (20/20, confirmed in the prior review) — but priority queues and fair-use windows are solving an allocation problem on top of a resource that periodically disappears entirely. That's not a scheduling failure; it's underneath the scheduler's remit, and no amount of EMA-tuned priority logic fixes a CUDA context that's gone. The "production line" metaphor implies a durable line that gets more efficient with tuning. What's been demonstrated twice now is closer to a line that stalls unpredictably regardless of tuning, at a rate high enough (55% failure on the lightest possible load) that no amount of scheduling sophistication built on top of it will be visible until the line itself is reliable.

The more encouraging read: the *research* production line — design an experiment, get criticized by multiple reviewers, redesign to directly answer each objection, attempt it, honestly report what happened even when it's a crash — is visibly working. EXP2's own structure, citing four separate reviewers by name against four separate sub-questions, is evidence of a functioning self-correction loop at the process level. The gap is that the *physical* production line (inference reliability) isn't yet solid enough to feed that process the data it needs. The epistemic machinery is ready to interpret a real result the moment one exists; it doesn't have one yet.

## Direct answers

**Do these results validate or undermine the DCA thesis?** Neither, cleanly — but if forced to pick a direction, *undermine*, for process reasons rather than content reasons. EXP1 falsifies its stated hypothesis (cognitive hit rate is not lower than command hit rate — it's higher) and leaves its rescue claim (neural embeddings save C2) unproven. EXP2 has not yet produced a single sham-arm data point across two attempts, meaning the one claim (C3) that actually tests whether DCA's central mechanism does anything remains completely untested, not disconfirmed. A dissertation that was already vulnerable to "zero experiments were run, all claims are projected" has, with these two attempts, moved from *zero experiments* to *two attempted experiments, one of which reverses its own hypothesis and one of which never reaches its own control condition*. That is progress on the honesty axis — real data collection is happening, and it's being reported straight, crashes included — but it is not yet progress on the "is the thesis true" axis, because the infrastructure keeps failing before the interesting question gets asked.

**What do they tell us about the production line model?** That the metaphor is currently aspirational at the hardware layer and real at the process layer. The scheduling logic (Logos, per the repo's own tripartite framing) is sound and tested in isolation. The thing it's meant to schedule keeps vanishing. Fix the CUDA reliability problem before trusting any further throughput or priority claims — and, separately, fix the exp2 analysis script's empty-sample bug before trusting any further p-value this pipeline produces. Both are infrastructure problems, not thesis problems, and both are cheaper to fix than either experiment was to run.

## What to do next

In order — each step is a precondition for the one after it, so do not skip ahead:

1. **Fix Ollama/CUDA reliability before rerunning anything.** Verify with the same check `ADVISORY_BRIDGE.md` already specified: `curl localhost:11434/api/generate` with a trivial prompt, confirm `>20 tok/s` and `size_vram > 0` via `/api/ps`, *before* relaunching any experiment. Two independent EXP2 runs have now died the same way — the earlier documented fix either wasn't applied or didn't hold, so verify, don't assume.

2. **Fix the empty-sample statistics bug in `exp2_analyze.py`/`update_report.py`** so that n=0 phases report "no data" instead of a fabricated `0.000 ± 0.000` that then feeds a t-test. This is a five-minute fix (guard on `n > 0` before computing comparison stats) and it's currently capable of producing a confident-looking null result from a phase that was never run. Fix before the next EXP2 attempt, not after, or the same misreading happens again.

3. **Rerun EXP2 with the CUDA fix verified, interleaved phases, and abort-on-failure rather than record-on-failure** (per `ADVISORY_BRIDGE.md`'s own recommendation, still unactioned) — order b,i,r,s,b,i,r,s,… so a crash at generation 10 costs 10 samples across all four arms instead of destroying entire arms, as happened here twice. This is the run that actually tests the thesis; nothing above this point does.

4. **Add the Conductor-vs-random-intervention arm** to whatever EXP2 run finally completes — the one comparison `CLAUDE_REVIEW.md` identifies as decisive and that still isn't in the design. Cheap to add once the four-arm harness is working; expensive to bolt on afterward.

5. **Do not rerun EXP1's neural-embedding check as an afterthought.** If C2 is going to be claimed as supported, rerun it properly: n=100 (not 8), real Granite-generated thoughts (not template fill-ins), a full threshold-sensitivity sweep at the neural embedding, and drop "cross-validation" as the label for what it is. Until then, treat C2 as falsified-as-tested with an unverified rescue hypothesis, not as supported.

6. **Fix the Mann-Whitney directionality in EXP1's writeup** (or standardize on two-sided tests throughout) — small, but it's the second statistics-pipeline bug found in two experiments, which is itself a signal: before either team member trusts the next p-value this project produces, it's worth one pass reviewing the analysis scripts specifically, separate from rerunning the experiments themselves.

These map directly onto items #1, #2, and #6 in `ethos/STRATEGIC_PRIORITIES.md`; this evaluation is independent empirical confirmation that #1 (the GPU/CUDA fix) is still the blocking item, and it surfaces one thing that document didn't have evidence for yet: the analysis pipeline itself needs a correctness pass before its output can be trusted.
